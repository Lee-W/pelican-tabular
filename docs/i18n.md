# Internationalization

The plugin resolves language at build time, in this order:

1. Shortcode `lang="ja"` (or a named view's `lang`).
2. The article/page's `Lang`.
3. This build's `DEFAULT_LANG`.
4. English.

An explicit shortcode language wins over the view's language. Each component
has its own `lang` and `dir`; JavaScript uses that component's language, including
sorting. Different languages can coexist on one page.

Tags are normalized (`zh_TW` becomes `zh-TW`). Exact translations win, followed
by a compatible parent or resource with the same language and script. Built-in
UI catalogs cover English, Traditional Chinese and Japanese. `zh-TW`, `zh-Hant`
and legacy bare `zh` use Traditional Chinese; `zh-Hans`/`zh-CN` fall back to
English until a Simplified Chinese catalog is provided. Unknown languages also
fall back to English. They do not change the component's selected language.

## Labels and messages

Display labels accept a string or a language-to-string mapping. This applies to
`TABULAR_FIELD_LABELS`, view `field_labels`, filter option `label`/`description`,
and preset `label`. Missing labels fall back to an English entry, then the
field key (or an empty optional description). An explicit empty translation is
preserved.

```python
TABULAR_VIEWS = {
    "works": {
        "fields": ["title", "category"],
        "field_labels": {"title": {"zh-TW": "作品名稱", "ja": "作品名"}},
        "filters": {
            "category": {
                "options": [
                    {
                        "value": "anime",
                        "label": {"zh-TW": "動畫", "ja": "アニメ"},
                    }
                ],
            },
        },
        "messages": {"search": {"zh-TW": "搜尋作品", "ja": "作品を検索"}},
    },
}
```

Filter values and URL query values remain `anime` in both languages.
`TABULAR_MESSAGES` sets site-wide messages; view `messages` overrides them.
Message keys are listed in the packaged `messages.json` catalog.

Count messages can use CLDR plural categories:

```python
TABULAR_MESSAGES = {
    "row_count": {
        "plural": "n",
        "forms": {"one": "{n} entry", "other": "{n} entries"},
    },
}
```

`row_count` and `group_count` require `{n}`; view `count` requires both
`{shown}` and `{total}`. Plural nodes require `other` and may also contain
`zero`, `one`, `two`, `few`, and `many`. Python uses Babel and JavaScript uses
`Intl.PluralRules`. A catalog fallback carries its own plural language, so
English fallback counts still distinguish `1 row` and `2 rows` on a Japanese
or unsupported-language component. Custom plural nodes use the component
language unless they specify `locale`.

The existing `TABULAR_COUNT_TEMPLATE`, `TABULAR_GROUP_COUNT_TEMPLATE` and view
`messages.group` remain supported; explicit empty count templates hide counts.
Legacy count templates may contain trusted HTML. New message/label values are
text. Invalid types, language tags or placeholders report their setting path
and fail the build instead of silently publishing an incomplete component.

## Optional record translations

Translation is opt-in. Ordinary dictionaries, links and reference records keep
their existing meaning. Enable translation for specific scalar text fields:

```python
TABULAR_TRANSLATIONS = {
    "field": "translations",  # may be renamed if this key is already in use
    "fields": ["title", "note"],
    "source_lang": "zh-TW",
    "aliases": {"ja": {"title": "title_native"}},  # optional migration mapping
}
```

```yaml
- id: a-silent-voice
  title: 聲之形
  title_native: 聲の形
  note: 來源備註
  category: anime
  translations:
    ja:
      title: 聲の形
```

A view may override this with its `translations` setting. Explicit record
translations take precedence over mapped alias fields. Missing translations
retain the source text; `source_lang` (default `und`) supplies its HTML language.
The source record and reference cache are never modified. The translation
payload is removed from the rendered projection, and internal language metadata
does not become an auto-detected column.

IDs, coordinates, link structures and numeric values cannot be translated.
Fields used for filtering or grouping must remain canonical; translate their
option labels instead. There is no automatic language guess for `title_native`.
Only explicitly configured `search_fields` are indexed by the view; add an alias
field there when it should be searchable. Translations are not automatically
made searchable or exposed as secondary titles.

`TABULAR_REF_TRANSLATIONS` accepts the same configuration for resolved reference
records (for example `fields: ["name"]`). References resolve by stable ID first;
their display text is then projected for the component language.

## Search, formatting and builds

Search uses Unicode NFKC plus lowercase on both sides. This ignores fullwidth
versus halfwidth differences and normalizes combining characters; it performs
no Simplified/Traditional conversion, translation or romanization.

Browser text sorting uses an explicit component locale. Initial Python sorting
retains the existing deterministic string order and may differ from browser
collation. Numeric/date sort keys retain their types. Explicit `date_format`
still wins; the plugin never changes the process locale.

Each Pelican build keeps separate language, root, URL and reference state.
Translated display text is already in the generated HTML for no-JS readers and
HTML indexers such as Pagefind. Pagefind's language-specific site configuration
and alias indexing remain the site's responsibility.
